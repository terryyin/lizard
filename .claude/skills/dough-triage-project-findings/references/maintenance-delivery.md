# Own and deliver the maintenance result

This invocation's explicit maintenance authority includes routine publication
of only its findings, canonical stories, reciprocal links and backlog changes.
The expressly named phase of a user-invoked combined cycle carries that same
authority for its established project. Do not ask for a second keep or publish
instruction once that authority and target are established. An explicit no-push
instruction still governs; preserve and report the unpublished result.

## Select an owned checkout before writing

Apply the shared [checkout ownership
lifecycle](../../dough-manual-testing/references/exploration-workspace.md), using
its selection, local-role/target recording and resume rules. This maintenance
supplies its own continuation below rather than preparation's keep question or
execution's Take/claim. Record the actual workspace, branch, starting revision,
created-versus-reused ownership, originating/default checkout when supplied,
and separately the authorized origin remote and branch.

Use an already established suitable owned maintenance workspace. Verify its
identity and inspect both committed and uncommitted work, including staged,
untracked and deleted paths. Dough Land publishes the whole checkout and every
unpublished commit above the fetched target, so a clean worktree alone is
insufficient. Reuse requires that the whole result to be landed contains only
this invocation's maintenance and previously retained work of this same
maintenance run. An explicitly selected checkout with other work cannot pass
that validation; stop its writes/publication and name the unrelated content.
Do not switch its branch, move others' edits or silently broaden the landing.

When no suitable checkout already owns this maintenance, select a fresh owned
workspace through that lifecycle using the freshly fetched, authorized origin
target as its verified base. Dirty files, staged content and unpublished commits
in the originating/default checkout stay there. Bring supplied uncommitted
evidence into the assessment only when explicitly selected as input; do not
copy unrelated edits into the maintenance candidate. Resolve this project's
worktree-location conventions rather than inventing a manager or registry.
If the target or safe selection is missing, stop the dependent write, preserve
resources and return the useful supported assessment with the exact gap.

Keep one verified workspace throughout the run and any interrupted delivery.
Do not replace it to evade an identity conflict, unresolved Git operation or
publication failure. If another owning workflow supplies its checkout, retain
that workflow's completion and retirement gates.

## Deliver the maintenance result

Before committing or publishing, validate the invocation's instruction against
the actual retained result and fetched target:

- The explicit user instruction, or the combined-cycle caller's passed user
  instruction, names this maintenance phase and target project. The selected
  remote and branch are unambiguous and authorized.
- Every committed/uncommitted difference to be landed is the reviewed
  maintenance result. No implementation, unrelated exploration, another
  session's work, or unpublished originating-checkout suffix is included.
- The independent supported edits are verified, reciprocal links are complete
  for claimed selections, and any unresolved decision is excluded from the
  candidate and reported. Partial completion does not expand authority.

A validated instruction under this section is this skill's narrow handoff to
[Dough Land](../../dough-land/SKILL.md), equivalent to its validated keep caller
for this maintenance result only. Invoke it without a further user question.
Supply the owned checkout and its recorded base/ownership, the selected origin
target, and the default checkout when established. Dough Land owns the commit,
reconciliation, remote acceptance, optional refresh, retirement and interrupted
landing mechanics; do not reproduce those steps or use an ad hoc push instead.
Apply the complete linked landing and publication procedures, including
[candidate retention before push](../../dough-execute-plan/references/publish-the-candidate.md#publish-the-candidate)
when applicable: retain the full candidate SHA and the base its owned suffix
extends before each push, then publish that pinned candidate as the shared
procedure requires. Loading Dough Land or passing its queued-closure check
alone does not complete the handoff.
This is ordinary reviewed metadata work unless retained context establishes an
execution: absence of a story or plan is not unfinished execution. When another
workflow owns the checkout, its gates still apply.

An unchanged result creates no empty commit. Inspect real local and remote
state and continue any interrupted landing from its first unfinished step.
Report synchronized only when the fetched authorized target contains the
retained maintenance result. Verify default-checkout state separately; a
deferred refresh preserves unrelated work and does not undo accepted
publication. Retain a stopped candidate with its checkout, branch, target and
exact recovery step. A conflict, uncertain push result or missing target is an
unfinished synchronization, not a successful run. Metadata publication does
not start an implementation mission or authorize unrelated CI repair.

After the landing operations settle, return to triage's report and apply
[completion attention](../../dough-land/references/completion-attention.md) to
the combined final wording. The ownership reasons and meaningful record/queue
outcomes are requested details of this triage invocation under that rule.
With supplied dashboard reporting context, defer its
[final completion operation](../../dough-land/references/dashboard-completion.md)
until the full triage response is settled; do not finalize the child landing
before that return. Apply the shared reporting procedure once, after all
required operations and wording have settled.
